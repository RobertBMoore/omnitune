# Portable Prompt-Tuner — Design Doc (v0.1, for audit)

## 0. Operator decisions locked (2026-06-14)

| Decision | Answer | Design consequence |
|---|---|---|
| Audience | Both technical + non-technical | Install wizard gauges skill level and adapts question depth |
| Distribution | Public / open-source | Zero client/company assumptions in core; neutral docs; no telemetry |
| Audit target | Design doc + working prototype | This doc + the `omnitune/` scaffold |
| Auto-sync UX | Just-in-time interrupt with skip/defer/snooze | §7 — never derails live work; operator owns the call |

## 1. Problem & goal

The `skill-tuner` system has two modes:

- **Mode A (`/omnitune:tune-skill`)** — audits a skill/agent file against the current Anthropic model's prompt-engineering best practices across a 7-dimension rubric; produces a severity-ranked report and applies interactive edits.
- **Mode B (`/omnitune:tune-prompt`)** — rewrites an ad-hoc user prompt into model-optimized form, self-scoring it in a QA loop before presenting.

Both are valuable but welded to the originating client repo: the skill list, routing keywords, domain pointers, anti-patterns, and output paths are all client-specific.

**Goal:** a portable, model-agnostic Claude Code plugin that any repo or business installs in minutes, configures through a guided interview, and that keeps itself tuned to the latest Anthropic model — so operators always get the best possible output from their Claude sessions, on whatever model is current.

## 2. The decoupling surface (what is client-coupled today)

| Source file | Coupled element | Portable replacement |
|---|---|---|
| `SKILL.md` | Hardcoded 7 client skills + prose routing | `omnitune.config` → `skills[]` map |
| `prompt-rewrite-protocol.md` §1 | client keyword→skill table | `omnitune.config` → `routing[]` |
| `prompt-rewrite-protocol.md` §2–5 | client campaign/brand/persona pointers | `omnitune.config` → `context_pointers[]` |
| anti-pattern / reserved-decision callouts | client `reference/06`, `reference/07` | `omnitune.config` → `house_rules`, `reserved_decisions` (optional) |
| `SKILL.md` Definition of Done | `reports/`, `docs/prompts/` | `omnitune.config` → `output.reports`, `output.prompts` |
| `references/opus-4-8-best-practices.md` | Model-version filename + `model:` | Stable filename `model-best-practices.md` + `model:` frontmatter (no rename churn) |
| `references/common-anti-patterns.md` | Generic prompt-eng smells (mostly portable) | Keep as-is; domain smells move to host config |
| `references/skill-md-template.md`, `agent-md-template.md`, `description-authoring-guide.md` | Generic (portable) | Keep as-is |

**Design change from source:** the client version renames the snapshot on a model bump (`opus-4-8-` → `opus-4-9-`) and rewrites every pointer. For a portable package that auto-updates, a **stable filename with a `model:` frontmatter field** is more robust — it removes the "update every pointer" failure mode. The model identity lives in metadata, not the path.

## 3. Package architecture

A **Claude Code plugin** (`omnitune/`) — chosen over a bare copy-in `skills/` folder because a plugin is the canonical install unit, namespaces its commands, ships its own wiki, and updates atomically without the host editing its `.claude/`.

```
omnitune/
  .claude-plugin/plugin.json        # manifest
  README.md                         # quickstart
  omnitune.config.example.yaml         # a client shown as ONE example
  omnitune.config.schema.md            # every field documented
  skills/
    omnitune/SKILL.md           # decoupled two-mode entry point
    omnitune/audit-protocol.md          # Mode A rubric (config-driven inputs)
    omnitune/prompt-rewrite-protocol.md # Mode B (config-driven routing)
    omnitune/references/        # model-best-practices.md + templates + anti-patterns
    install/SKILL.md          # install-time auditor loop (the wizard)
    sync/SKILL.md             # auto-patch auditor loop + model detection
  commands/
    tune-skill.md  tune-prompt.md  install.md  sync.md
  wiki/
    Home.md  How-It-Works.md  Install-Setup.md  Configuration.md  Auto-Sync.md  FAQ.md
```

**Rejected alternative:** a bare `skills/` copy-in (no manifest). Lighter to author, but the host must hand-wire commands, there is no clean update path, and the wiki has nowhere to live. Plugin wins for a public artifact.

## 4. The config layer (`omnitune.config.yaml`)

The single customization point. Generated by the install wizard (§5), human-confirmed, then read by every run.

```yaml
project:
  name: "<repo or business name>"
  domain: "<one line: what this repo/business does>"
skills:
  root: "skills/"            # where the host keeps its skills
  agents: ".claude/agents/"  # optional; "" if none
routing:                      # keyword → skill, for Mode B target detection
  - skill: "<name>"
    keywords: ["...", "..."]
context_pointers:             # files Mode B should cite when a target is detected
  - when: "<skill or topic>"
    point_to: ["path/a.md", "path/b.md"]
house_rules: "<path to anti-patterns/voice/style file, or ''>"
reserved_decisions: "<path to decisions the tuner must surface-not-preempt, or ''>"
output:
  reports: "reports/"
  prompts: "docs/prompts/"
model_sync:
  channel: "interrupt"        # see §7
  snooze_default: "24h"
  regression_corpus: "tuner/regression/"   # saved prompts/skills to re-score on a model bump
```

The **core package contains zero client-specific strings**; the client's real values live only in `omnitune.config.example.yaml`.

## 5. Install-time auditor loop (the wizard)

Setup is not a static config file — it is an **interview that audits its own understanding before writing anything.**

```
1. DETECT      Scan the host repo: read CLAUDE.md/AGENTS.md, list skills/agents,
               sample a few SKILL.md files, infer domain + conventions.
2. GAUGE       Ask 1 calibration question → set interview depth:
               technical operator → terse, config-shaped questions;
               non-technical → plain-language, one concept at a time, with examples.
3. INTERVIEW   Ask as many questions as needed to fill every config field with
               confidence: domain, skill list, routing keywords, house rules,
               voice/style source, reserved decisions, output paths. Ambiguity
               → ask; never guess a field.
4. REFLECT     Restate the understanding in plain language + show the draft config.
               "Here's what I learned about your repo — did I get it right?"
5. CONFIRM     Operator approves / corrects. Loop 3–5 until approved.
6. DRY-RUN     Validate by doing: rewrite one sample prompt (Mode B) and audit one
               sample skill (Mode A) using the draft config. Show results.
7. WRITE       Only now write omnitune.config.yaml. Print a one-line "you're set up"
               + how to run each mode.
```

**Fail-closed:** nothing is written before step 7's confirmation; a low-confidence field blocks completion until asked. This mirrors the operating principle that *the agent is not the auditor of its own work* — the operator is the final reviewer of the context the wizard built.

## 6. Mode A / Mode B (logic unchanged, inputs config-driven)

The two modes keep their existing protocols (`audit-protocol.md`, `prompt-rewrite-protocol.md`). The only change: every client-hardcoded input (skill list, routing table, pointers, paths) is now read from `omnitune.config`. The 7-dimension audit rubric and the Mode B QA loop are model-best-practice-driven and unchanged.

## 7. Auto-patch auditor loop + model-sync (the self-tuning engine)

This is the heart of "always operating optimally." It is an **audit loop, not a version bump** — when Anthropic ships a new model, the plugin reasons about *what behavior changed* and *whether that changes how it should tune prompts*, asks the operator what it can't resolve, and only then patches itself.

### 7a. Detection (just-in-time)

At the **start of every `/omnitune:tune-skill` or `/omnitune:tune-prompt` run**, the freshness gate:
1. Reads the snapshot's `model:` + `lastSynced`.
2. Checks Anthropic's published model list for a newer **GA** model (preview/research-preview models like fast mode are ignored to avoid false positives).
3. If a newer GA model exists → fire the interrupt (7b). Else → proceed normally.

### 7b. The interrupt UX (operator's design)

On detection, **halt the current task** and surface:

```
⏸  A newer Anthropic model (claude-opus-4-9) is available.
   Your tuner rubric is tuned for claude-opus-4-8 (synced 2026-06-04).
   Tuning against a stale rubric may not produce the best prompts for the new model.

   How do you want to handle it?
   [u] Update now — open a dedicated update session (asks questions, gets approval), then return you here
   [s] Skip for this session — don't ask again until next session
   [d] Defer — finish my current task(s) first, then offer the update
   [z] Snooze until <time> — re-ask after the window (default 24h)
```

The operator can always jump straight back into the original task. The choice (and snooze deadline) persists in `tuner/.sync-state.json` so it is honored across the session/window.

### 7c. The behavioral diff (the actual audit)

When the operator chooses **Update now**, a dedicated session:
1. Fetches the new model's docs (what's-new, migration guide, prompting best practices).
2. **Diffs behavioral changes** against the current snapshot — literalness, effort calibration, tool-triggering, subagent defaults, new capabilities.
3. Classifies impact on: (i) the best-practices rubric, (ii) Mode A's 7 dimensions, (iii) Mode B's rewrite heuristics, (iv) the operator's own domain workflow (e.g. "the new model is more literal — your campaign prompts may need explicit scope you previously relied on inference for").
4. Where impact is ambiguous or touches the workflow, **asks the operator targeted questions** ("the new model changes X; do you want the rubric to enforce Y?").
5. Drafts the patch.

### 7d. Apply + verify

1. Regenerate `model-best-practices.md` (update `model:`, re-derive rules, stamp dates).
2. **Regression check:** re-score the host's `regression_corpus` (saved known prompts/skills) under the new rubric; flag any item whose verdict flips, so silent quality drift is caught.
3. Present the diff + regression result for **human approval** before committing.

### 7e. Safety invariant

Detect-and-propose, **never silent self-commit.** The plugin must not grade its own rewrite of its own rubric without a human gate — this is the "agent is not the auditor of its own work" principle applied to the tool's own brain. The interrupt model (7b) and the approval gate (7d) are both enforcements of it.

## 8. Wiki plan

`Home` (what/why) · `How-It-Works` (both modes, QA loop, rubric, freshness contract) · `Install-Setup` (plugin install + the wizard walk-through) · `Configuration` (every field, worked example) · `Auto-Sync` (the interrupt + behavioral-diff loop) · `FAQ` (troubleshooting, offline fallback, "how do I add a skill to routing").

## 9. Open questions & risks (for the auditors and the operator)

1. **Model-list source of truth.** There is no single official "latest GA model" endpoint. Detection may rely on scraping the models doc/changelog — risk of false positives (previews) or misses. Need a reliable signal.
2. **Snooze persistence.** `tuner/.sync-state.json` is per-repo; what about a global operator preference across repos?
3. **Regression corpus seeding.** Who populates it per host, and how big must it be to catch drift?
4. **Non-technical depth ceiling.** How deep can the wizard really build context for a non-technical operator before it needs a human collaborator? Is there a "call your developer" escape hatch?
5. **Open-source trust.** The model-check needs network access; offline/air-gapped hosts need a manual-refresh fallback. No telemetry — confirm.
6. **Mode B "worse rewrite" risk.** The QA loop caps at 2 redrafts; on a new model the heuristics may be wrong until synced. Does the interrupt fire *before* a rewrite to avoid shipping a stale-model rewrite?

## 10. Success criteria (Definition of Done)

- A single top-level package folder; core grep-clean of client-specific strings.
- Install wizard builds a correct config via interview + dry-run, on both a technical and a non-technical operator path.
- Auto-sync detects a newer GA model, interrupts with the four options, runs the behavioral-diff audit, asks questions, and applies only after human approval + regression check.
- Wiki complete (6 pages) + one-page quickstart.
- Smoke test: copied into a scratch repo, `/omnitune:install` produces a config, then `/omnitune:tune-prompt` and `/omnitune:tune-skill` both run against that repo.
